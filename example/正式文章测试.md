# 服务端可观测性建设：从日志到统一的遥测体系

传统的单机排障手段在这样的拓扑里迅速失效，工程师面对的不再是一个可以登录进去查看的机器，而是一张不断变化的服务依赖图。可观测性（Observability）要解决的正是这个问题：通过系统对外输出的遥测数据，还原任意时刻系统的内部状态。

排印之外，可观测性本身也有自己的骨架。遥测数据按形态分三类，各自的 `trace_id`、时间序列与事件字段在管线里走不同的通道，对照着看最清楚：

| 数据形态 | 回答的问题 | 保留成本 | 典型后端 |
|:---|:---|:---|:---|
| 日志 | 某一时刻发生了什么 | 高 | Loki |
| 指标 | 系统整体健康程度如何 | 低 | Prometheus |
| 追踪 | 一次请求经历了哪些环节 | 中 | Tempo |

采集端只需一份极薄的配置，就能把三类数据送往各自的后端：

```yaml
otelcol:
  receivers: [otlp]
  processors: [batch]
  exporters: [prometheus, loki, tempo]
```

## 为什么日志不够用了

日志是历史最悠久、也最容易被滥用的遥测手段。它记录离散的事件，适合回答「某一时刻发生了什么」，却很难回答「系统的整体健康程度如何」。当一次接口抖动牵涉网关、认证服务与三个下游依赖时，逐台机器翻找日志的成本会指数级上升。

更实际的困境在于成本。全量日志的存储开销常年占据可观测性预算的一半以上，而其中绝大多数条目在产生后的七天内从未被查询过。一个常见的折中是按日志等级分层保留：`ERROR` 与 `WARN` 保留九十天，`INFO` 保留十四天，调试日志只进本地磁盘并在滚动时丢弃。

```bash
# 以 Loki 为例，按服务与等级双维度打标签
loki:
  schema_config:
    configs:
      - from: 2024-01-01
        store: tsdb
        object_store: s3
        schema: v13
  limits_config:
    retention_period: 720h
```

## 指标：用数字描述系统的形状

指标把连续的系统状态压缩成可聚合的时间序列，是三类遥测数据中成本最低、报警价值最高的一类。延迟分布不能只看平均值，第 99 百分位与第 999 百分位才能暴露长尾；错误率要与流量一起看，低峰期的百分比往往具有欺骗性。

### 黄金四信号

Google SRE 提出的四个信号至今仍是报警设计的起点：延迟、流量、错误与饱和度。每一类服务都能把这四项映射成具体的指标名，映射表一旦固定，不同团队的面板与报警就有了共同语言。

### 指标命名的纪律

混乱的指标命名会让面板变成考古现场。团队应当约定统一的前缀、单位后缀与维度下界，例如所有计数器以复数名词结尾、所有耗时以毫秒为单位并用 `_seconds` 声明。命名规范本身不产生数据，但决定了两年之后这些数据还能不能被人读懂。

## 链路追踪：还原一次请求的完整旅程

链路追踪在分布式系统中引入了 Trace 与 Span 两个概念。Trace 是一次请求的全局编号，Span 是其中一个处理段，父子 Span 构成一棵调用树。有了这棵树，「慢」不再是一个模糊的感受，而是可以被逐层拆解的归因过程。

### 采样策略

全量追踪的成本难以承受，主流方案是头部采样与尾部采样的组合。头部采样在请求入口就决定是否记录，成本确定但可能丢掉关键故障；尾部采样等请求结束后再决策，能完整保留慢请求与错误请求，代价是中间节点必须缓存全部数据。

### 上下文传播

追踪的真正难点不在存储端，而在传播链路的每一跳。HTTP 头、gRPC 元数据、消息队列的消息属性都要正确携带上下文，任何一个环节断链，调用树就会裂成孤立的碎片。跨语言的团队应当把传播逻辑封装进统一的中间件，而不是让每个服务自行实现。

## 事件与结构化日志

结构化日志是日志与事件之间的折中。每条日志是一个 JSON 对象，字段名遵循约定，级别、服务名、追踪编号一一对应。查询引擎可以像查数据库一样按字段过滤，而不是用正则表达式在自由文本里碰运气。

```json
{
  "level": "error",
  "service": "order-api",
  "trace_id": "4bf92f3577b34da6",
  "span_id": "00f067aa0ba902b7",
  "message": "downstream payment timeout",
  "elapsed_ms": 3007
}
```

### 日志与追踪的关联

把 `trace_id` 写进每一条结构化日志，是打通两类数据最便宜的手段。报警触发后，值班工程师从指标面板跳到追踪列表，再从异常 Span 跳到对应日志，三次点击完成一次完整的排障路径。

## 统一的遥测管线

三类数据分属三套存储与查询语言，是当前可观测性领域的最大碎片。OpenTelemetry 的目标是把采集端统一：应用只关心如何产生数据，导出到哪个后端由配置决定。采集器独立部署后，应用进程里的埋点客户端变得极薄，升级与采样策略都收敛到管线层。

### 采集器的部署形态

常见部署分两种：以 Sidecar 形式随应用调度，网络路径最短；以 DaemonSet 或网关形式集中部署，运维成本最低。多数团队的选择是两者混合，边缘做转发与缓冲，中心做采样与脱敏。

## 仪表盘的设计原则

仪表盘不是数据的仓库，而是问题的索引。一个服务的主面板应当在一屏内回答四个问题：流量是否正常、延迟是否恶化、错误是否抬头、依赖是否饱和。回答不了的细节留给下钻面板，而不是堆在首页。

### 面板与报警的对应

每一块面板都应该有一个对应的报警阈值，反之亦然。没有报警的面板是装饰，没有面板的报警是恐吓。两者成对出现，值班工程师才能在报警响起时立刻知道去哪里确认。

## 成本与数据的生命周期

遥测数据的体量以每天 TB 计，生命周期管理必须与采集同步设计。热数据保留在支持高频查询的存储里，冷数据压缩归档到对象存储；采样率随时间衰减，三十天前的原始 Trace 通常不再有查询价值。

```yaml
traces:
  sampling:
    default: 1%
    rules:
      - service: payment-api
        latency_ms: 500
        keep: 100%
  storage:
    hot: 7d
    cold: 90d
```

## 落地的顺序

可观测性建设不必一步到位。务实的路径分四步走：先统一日志格式并关联追踪编号，再为核心服务补齐黄金四信号，然后引入全链路追踪与尾部采样，最后收敛到统一的遥测管线与面板规范。每一步都有独立的收益，前一步的产出正好是后一步的输入。

工程的判断最终要回到问题本身：遥测体系不是为了收集数据，而是为了在凌晨三点的报警响起时，让值班的人用最短的时间回到睡眠。
